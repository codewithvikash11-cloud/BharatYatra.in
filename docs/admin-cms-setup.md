# Admin CMS setup and owner actions

## Admin authentication

The Content Studio uses one environment-configured admin credential, verified on the server with bcrypt. It does not use Supabase Auth. The app signs an eight-hour admin session with `ADMIN_SESSION_SECRET` and stores it in an HttpOnly, SameSite=Lax cookie that is Secure in production. Failed sign-ins are rate-limited in the admin process.

Keep `ADMIN_EMAIL`, `ADMIN_PASSWORD_HASH`, and `ADMIN_SESSION_SECRET` in the ignored root `.env` or the deployment secret manager. Never use `NEXT_PUBLIC_` variables for these values. For local setup, run `npm run admin:setup --workspace=@bharatyatra/admin` in an interactive terminal. It prompts for the admin email and a new password without echoing the password, rejects passwords shorter than 16 bytes, hashes the password, generates a random session secret, and writes only those values to root `.env`. Restart the admin and API servers after setup. Do not use the password previously shared in chat.

In production, set all three variables through the hosting platform's server-side secret settings. Use a unique password of at least 16 characters and regenerate the session secret to revoke all existing sessions. Supabase PostgreSQL remains the application database; Supabase Auth users and roles are not used for admin login.

## Content and status transitions

Existing database status values are `DRAFT`, `REVIEW`, `PUBLISHED`, and `ARCHIVED`. There is no `APPROVED` value in the existing schema. Editors can create/edit drafts and submit drafts for review. Admins can return review records to draft, publish reviewed records, unpublish published records to draft, archive records, and restore archived records to draft. The HTTP `DELETE` content operation is a soft archive and never deletes rows. Attractions can be published only when their destination is published.

Review submission checks required factual copy columns already in the Prisma schema: destinations need English summary and description; attractions need English description and category; articles need English excerpt, body, and author name. No travel facts or sample content are generated by the CMS.

## Audit migration (not applied)

`supabase/migrations/20261001142309_admin_audit_logs.sql` is a local additive migration. It creates `public.admin_audit_logs`, two indexes, enables RLS, constrains action/entity names, and revokes access from `PUBLIC`, `anon`, and `authenticated`. No existing table, row, RLS policy, or migration-history record is changed. The matching Prisma model is in `prisma/schema.prisma`.

Before any owner applies it, review the SQL and backup/rollback expectations. Then have the database owner apply the reviewed migration using the project’s approved Supabase migration process, and run the read-only API and admin audit checks. Do not run `db push`, `migrate reset`, or destructive SQL. This repository has not applied the migration to the remote project. Admin mutations use a Prisma transaction that includes an audit record, so they fail/rollback until this table exists.

## Media storage (not configured)

The workspace currently has no storage bucket. Set `MEDIA_STORAGE_BUCKET` only after an owner creates a private bucket with the intended size limit. The custom admin session is not a Supabase Auth token, so the API validates the session and image signature before using `SUPABASE_SERVICE_ROLE_KEY` server-side for uploads. This key bypasses Storage RLS and must never be exposed to the browser; do not grant public writes. Uploads are limited to JPEG/PNG/WebP/AVIF with verified file signatures and a 5 MB cap. Until the bucket exists, upload is unavailable.

The existing `media_assets` public-read policy remains unchanged. Store public URLs only if the owner intentionally chooses public media. Private buckets need signed-URL delivery support before assets can be rendered by public pages.

## Local configuration and commands (Windows PowerShell)

From repository root:

```powershell
if (-not (Test-Path .env)) { Copy-Item .env.example .env }
npm install
npm run dev:api
```

In separate PowerShell windows:

```powershell
npm run dev:admin
npm run dev:web
```

Required local values: `ADMIN_EMAIL`, `ADMIN_PASSWORD_HASH`, `ADMIN_SESSION_SECRET`, `SUPABASE_URL`, `SUPABASE_SERVICE_ROLE_KEY` (server-side media uploads only), `NEXT_PUBLIC_API_BASE_URL`, `ADMIN_ORIGIN`, `DATABASE_URL`, and `DIRECT_URL`. The website's public Supabase settings remain available for its existing database/public-content functionality. The API uses database and service credentials only server-side. `.env` must remain ignored by Git. Never add a service-role/secret key to browser-exposed variables or website code.

Useful checks:

```powershell
npm run check
npm test --workspace @bharatyatra/api
npm test --workspace @bharatyatra/web
npm run build
npm run prisma:validate --workspace @bharatyatra/api
npm run prisma:generate --workspace @bharatyatra/api
```

Before admin launch: configure the three admin environment variables, review/apply the audit migration, configure a private storage bucket if media upload is needed, then verify login, protected pages, API mutations, logout, and session expiry. The login does not create user accounts; password changes are performed by rerunning the local setup command or by updating the server-side environment through the approved deployment process.
